# 确认与幂等协议

## 三类重复必须区别

1. **重复捕获**：用户对同一消息连续 Ping，合并到已有草稿/任务。
2. **重复派发**：双击确认、进程恢复、网络重试，同一个提交轮次不能生成新任务。
3. **任务续接**：新增信息或明确要求重新执行，产生新的提交轮次，通常继续已有外部会话。

重复 Ping 不等于续接；截图相似也不等于同一个业务任务。

## 标识

来源键：

`platform + account/tenant + conversationID + messageID`

意图匹配键：

`sourceKey + stableActionID + executorProfileID`

执行器在生产中使用稳定 ID，不使用可修改的显示名称。原型使用固定演示名称。

任务 ID：内部 UUID。提交 operationID：由 `taskID + revision` 得出。payloadHash 单独存储，不用截图哈希替代业务标识。

同一个 operationID 的 payload 永远不变。提示词、上下文或补充说明变化后必须形成新 revision，不能复用旧 operationID。

模板版本不直接导致重复 Ping 新建任务：重复 Ping 先打开已有记录，并告知模板变化；用户决定是否更新草稿或明确创建新一轮。

尚无稳定消息 ID 时，使用 captureID 保存独立草稿。窗口/OCR/图片指纹只能提示“可能重复”，不能在证据不足时自动合并。识别完成后重新核对来源键。

## 确认规则

| 情况 | 行为 |
|---|---|
| 同来源、同动作、同执行器，已有草稿 | 打开草稿，保留用户编辑 |
| 同目标已排队 / 执行中 | 显示当前任务，不新增提交 |
| 已完成，没有新增信息 | 展示结果 |
| 已完成，有新增信息 | 用户确认“补充并继续”，生成下一轮 |
| 同消息选择不同动作 | 新草稿，同时提示有关联记录 |
| 同消息切换执行器 | 新草稿，确认卡突出目标变化 |
| 不同消息疑似同一件事 | 推荐已有任务，由用户确认关联 |
| 明确要求重做或另开任务 | 显式动作，新轮次或新 taskID |
| 草稿已取消，再次 Ping | 新建草稿 |

“继续推进”在生产版必须选择关联任务；不能仅凭动作名决定续接对象。原型的“继续推进”轮盘项仅演示提示词，真实续接通过已有记录里的按钮演示。

## 提交流程

1. 校验来源、执行器和内容；歧义未解决则停留在草稿。
2. 用户明确确认。
3. 数据库事务：冻结 payload，写 Submission 与 outbox，状态 queued。
4. 派发器领取队列；同一 task 同时最多一个活跃轮次。
5. 调用执行器并附 operationID（如支持）。
6. 成功后保存 externalID，转 accepted/running。
7. 输出事件持久化后更新界面；done 不自动代表验收通过。

数据库唯一约束：`Submission(taskID, revision)`、`operationID`。事件去重依赖 externalEventID 和 adapter 范围。

双击确认由内存状态保护和数据库约束共同阻止，不能只禁用按钮。

## 超时、崩溃与恢复

最危险情况：执行器已创建任务，但 App 没收到回执。

- 对方支持幂等键：用原 operationID、原 payload 重试。
- 对方支持按请求 ID 查询：先核对结果并补存 externalID。
- 两者都不支持：标记 outcomeUnknown，停止自动重派，提供人工核对。

没有远端配合时不能承诺端到端 exactly-once。目标是本地不重复提交、可恢复、结果未知时不盲目重试。

重启后恢复 queued；对 dispatching/unknown 先核对；对 running 查询状态。不能因为本地断开就把任务标记失败并新建一份。

取消草稿不影响远端；取消已接受任务必须得到执行器确认。关闭 App 不代表远端已取消。

## 原型实现范围

已实现：意图匹配、草稿复用、状态提交保护、逐轮 operationID、提示词快照、显式续接、原子保存、重启将未结束模拟任务标记待核对。

后续第一期已加入 Codex CLI 初次真实派发：独立 SQLite 保存唯一提交，事务领取后启动 tmux，worker 使用排他启动标记，未知结果不自动重发。任务元数据仍为 JSON；远端去重、跨客户端状态同步、关联不同源消息、主动重做和真实取消仍未实现。详见 [CLI 交接](06-codex-cli.md)。

### 当前原型补充
按用户最新要求移除项目维度，任务去重使用来源、动作 ID、执行器。旧 JSON 的 project 字段读取时忽略，历史 operationID 不重算。仅特效动作不进入确认/派发状态机。取消支持草稿与本地模拟执行中；删除先持久化移除记录，再将未被其他记录引用的截图移入废纸篓。清理失败明确提示并保留文件；真实执行器取消仍未实现。

## 用户主动配置的自动处理补充（2026-10）

默认仍需人工确认。用户可在单个意图开启自动上下文及自动提交，以预先授权代替逐次点击。仅唯一匹配且上下文未截断时可提交，歧义留草稿，已有任务不自动重发。提交仍冻结快照并经过相同 SQLite 占用流程；完成不代表验收。详见 [WorkBuddy 与自动处理配置](07-workbuddy.md)。

微信自动绑定补充：OCR 只提供检索线索，低分可先查询 wxview。允许自动绑定需唯一精确会话、完整规范化指针长文本（至少 12 个字母/数字/汉字）包含于唯一 wxview 文本消息、上下文未截断，并已开启对应意图的自动处理。只命中检索片段、同名会话、多消息或截断均保留候选供人工确认。看图推断不替代稳定消息身份；打开旧记录只读取候选，不触发自动提交。
